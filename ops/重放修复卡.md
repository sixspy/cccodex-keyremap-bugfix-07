# 重放修复卡（定稿 · 当日禁止改口）

- 定稿日期：2026-11-20
- 题目域：实体键桥（07-keyremap），库：本地 SQLite，登录沿用现有 `/api/login` Bearer 会话
- 修复对象：冲突重放写路径的**无痕覆盖**——重放后正式内容被改，但重放审计与 generation 未抬升、被盖版本无快照可溯、互证按世代对不上。

## 1. 入口约束（不另起重放台）

- 重放只能从**冲突区**既有冲突条目发起：`POST /api/conflicts/{conflict_id}/replay`，挂在现有 `/api/conflicts` 资源下，不新建独立 replay 站点/独立队列。
- 登录沿用 `require_user`（Bearer token），不新增认证方式。
- 冲突区行内按钮即重放入口，不另开页面。

## 2. 正确性口径：甲/乙两条互斥路径，一次重放只能走其一，禁止混用

判定依据：以生效映射版本重映冲突 `old_key` 得到目标 `entity_key`，与正式区同 `entity_key` 现态比较。

### 甲路径（幂等跳过，正式零改）
- 条件：目标 `entity_key` 已在正式区，且现态 `mapped_from` 与 `version` 与本次重放结果**完全相同**。
- 动作：正式表一行不写、不改；只写一条 `replay_audit(event='replay_skip')`，审计内记录 conflict_id、目标键、判定依据与当前 generation。
- 结果：正式零改，generation 不抬升，不产生世代行。

### 乙路径（带审计覆盖，同事务抬 generation + 被盖快照）
- 条件：目标 `entity_key` 不在正式区（新插入），或在但现态与本次结果**不同**（覆盖）。
- 动作必须在**同一个数据库事务**内完成：
  1. 覆盖前先把被盖行整体复制进 `entity_generations`（被盖快照：entity_key、mapped_from、version、created_at、被盖时的 generation）；
  2. 正式区 upsert 为新内容，`generation = 旧值 + 1`（新插入从 1 起）；
  3. 写 `replay_audit(event='replay_apply')`，记录新旧 generation 与快照 id；
  4. 冲突状态置「已重放」并回填 replay_id。
- 任一步失败：**正式表与快照一同回滚**，审计不留半条，接口返回 5xx，不得留下只改一半的正式内容。

### 互斥红线
- 禁止「覆盖了却只写 skip 审计」「跳过了却抬 generation」等混用；禁止只改重放成功提示文案充数——只改提示一律判失败。
- 偏离本卡的写请求拒写，并在审计落 `event='replay_deviation'`（偏离仅记录，不触发正式写）。

## 3. 并发占锁（同 conflict_id）

- `replay_locks(conflict_id INTEGER PRIMARY KEY, holder TEXT, acquired_at TEXT)` 为占锁点。
- 两路同 `conflict_id` 重放必须占锁：后到者拿不到锁即判争用，不等待改写，返回 `409 replay_contention`，只写 `replay_audit(event='replay_contention')`，正式零改。
- 锁在请求事务结束（提交/回滚）时随事务释放；不同 conflict_id 互不阻塞。

## 4. 五处同态（冲突区、正式实体、重放审计、世代列表、互证页）

同一重放事实在五处口径一致，可互相对账：

| 处 | 载体 | 必须体现 |
|----|------|----------|
| 冲突区 | `conflicts` 表 + `/api/conflicts` + 前端冲突队列 | 状态 挂起/已重放、replay_id、行内重放按钮 |
| 正式实体 | `formal_entities`（增 generation 列）+ `/api/formal` | 当前世代内容与 generation |
| 重放审计 | `replay_audit` + `/api/replay-audits` | skip/apply/contention/deviation 全事件、conflict_id、世代号 |
| 世代列表 | `entity_generations` + `/api/generations` | 每次覆盖的被盖快照与世代号，新插入不产快照 |
| 互证页 | 后端 `replay_crosscheck` 视图 + `/api/crosscheck` + 前端互证页签 | 按 entity_key+generation 把正式现态、世代链、审计、冲突逐行对齐 |

互证判据：正式区每个实体的当前 generation = 世代链最大世代 + 1（无快照时为 1）；每条 apply 审计都能在世代链指到一条被盖快照；每个「已重放」冲突都有一条 apply 或 skip 审计；有断链即标记 `mismatch`。

## 5. TDD 强制顺序（禁止跳过失败测、禁止无复现改提示）

1. 先复现「覆盖无审计」：红测 `test_replay_overwrite_without_audit_is_traced`——同键不同内容重放后，必须有 apply 审计、generation 抬升、被盖快照可查；现状无重放/审计/世代，测见红。
2. 再落「抢放争用」：红测 `test_concurrent_replay_same_conflict_lock_contention`——同 conflict_id 两路并发，后到者 409 且只落 contention 审计、正式零改；测见红。
3. 两条红测齐后才准改重放写路径；补齐甲路径、回滚、互证等同态测试，全绿后方可收尾。
4. 严禁先改提示/先写实现再补测；红测阶段禁止改 `backend/app.py` 写路径。

## 6. 完成判据（全绿后可查）

- 甲路径：重复重放同内容 → 正式零改、仅 `replay_skip` 审计、generation 不变。
- 乙路径：异内容重放 → 同事务内 generation 可查、被盖快照可查、apply 审计可查；注入快照失败时正式与快照一起回滚。
- 争用：同 conflict_id 并发 → 后到 409、仅 contention 审计。
- 五处同态：互证页无 mismatch；前端五个页签数据与接口一致。
- 本地夹具 + SQLite 全量 `pytest` 通过。

## 7. 执行结果（2026-11-20 验收记录，口径未改口）

- TDD 顺序留痕：先落两条红测（覆盖无审计、抢放争用），确认红后才动写路径；未跳过任何失败测、未先改提示文案。
- 关键落地决策（不改变第 2 节甲乙口径，仅落地手段）：
  - 重放事务用 `isolation_level=None` + `BEGIN IMMEDIATE` 显式事务，占锁/快照/正式写/审计同提交同回滚。
  - 库切 **WAL** + 200ms `busy_timeout`：delete 日志模式下同进程写锁会排队到赢家提交，无法即时判争用；WAL 下后到者即时拿锁失败，只记 `replay_contention`，业务写不排队。
  - 争用者自身写事务未开成，争用审计经独立短连接（5s 写锁等待窗口）落库，保证「后到只记争用」也有审计。
  - `replay_locks` 是互斥原语：成功提交前主动 `DELETE`，异常路径随 rollback 丢弃，不残留。
  - 正式写入口 `_upsert_formal` 改显式 SELECT-UPDATE/INSERT，兼容无 UNIQUE 约束的老库迁移。
- 验收：`pytest -q` 9 passed（原 smoke 1 + 重放 8），连续多轮稳定；争用测连跑 5 次全绿；旧库副本迁移加列加表、旧数据保留；端到端活体走通乙覆盖→甲跳过→互证 ok→401→重复重放 409。
- 测试清单：`tests/test_replay.py`（两条规定红测）、`tests/test_replay_paths.py`（甲跳过、乙新插入、快照失败整体回滚、偏离拒写、五处互证、登录沿用）。
